# 启动性能与完整就绪体验（ADR-005）

本方案以用户可立即开始工作为目标：**宣布运行时就绪之前，必须完成官方完整 SDK 的导入和校验。**
模型与会话目录就绪后，创建会话、进入插件管理或读取资源不再补载 SDK。

先前的目录入口及 SDK 懒加载适配已移除。原先的“窗口 3.83 → 2.32 秒、提升约 40%”
依赖将约 1.8 秒转移到首次操作，该结论已撤回，不能作为当前方案的性能结果。
当前直接返回官方 SDK 的完整模块对象，也不再依赖其内部 `dist/core` 文件布局。

保留并完善的优化：

- 构建时准备内置 Node.js 24.14.0 LTS、官方 npm/npx 11.9.0、Pi SDK 0.84.2。
  SDK 生产依赖通过 `runtime/package-lock.json` 锁定；Node 归档验证官方 SHA-256。
- 应用启动不下载、安装、解压运行时；构建准备支持缓存、互斥锁、健康检查与失败回滚。
- 仅当首选运行时校验或启动失败时探测备用来源，避免健康内置环境仍等待本地 PATH。
- 同一次启动不重复尝试失败的缓存候选；保留已有 Rust 启动互斥和关闭逻辑。
- Node 版本在 SDK 导入前预检。本机默认 Node 22.18.0 不满足 22.19 下限，
  预检实测约 238 ms 拒绝且没有导入 SDK，保持原有 `NODE_VERSION_UNSUPPORTED` 错误码。
- 使用 Node 内置编译缓存减少重复工作；缓存不可用时正常加载 SDK，不改变功能就绪标准。
- 内置 Node 的工具路径仅在 Bridge 子进程内生效，支持 npm/npx；不改系统 PATH。

完整 SDK 导入是必要工作，不将其视为可以牺牲的功能。此前 CPU 采样表明，
模块包作用域检查、文件读取和编译是重要开销。因此在相同完整 SDK 上对兼容的 Node LTS
运行时进行实测，再选择能够同时改善启动与操作等待的版本。

就绪回归测试使用延迟的 import Promise，确认未完成导入时不会返回就绪；
就绪后首次创建会话直接调用原始 SDK 函数，不产生第二次导入。
旧安装目录即使残留目录入口标记，也不会重新启用懒加载。

基准同时记录：进程到完整 SDK 握手、目录就绪、第一次会话请求的响应时间、
后续会话请求的响应时间和进程到首个会话完成的总时间。仅比较启动动画耗时不再算优化成功。
每组使用六个新进程及隔离的 HOME、agentDir 和工作区；每组第一个样本单列，后五个取中位数。
不清空操作系统缓存，不将这些测试称为机器重启后的冷启动。

```powershell
pnpm runtime:prepare
pnpm --dir agent-bridge build
$env:PI_BENCH_VERIFY_ECOSYSTEM = '1'
node scripts/benchmark-startup.mjs
```

基准还会检查模型/会话列表、两次会话创建、插件/资源/命令列表及正常 shutdown，
任何业务响应错误都会使测试失败。可传入 Node 和 SDK 的绝对路径进行相同 SDK 的运行时对照。
`PI_BENCH_DISABLE_CACHE=1` 只用于比较缓存开关，双方仍先加载完整 SDK。

主要文件为：`runtime/` 的版本和依赖锁定、`scripts/prepare-runtime.mjs` 与测试、
`scripts/benchmark-startup.mjs`、Bridge 的 `sdk-loader.ts`、`compile-cache.ts`、
`runtime-tools.ts`、`cli.ts` 及测试，以及 Rust 的 discovery/runtime/protocol。
会话运行时恢复原有实现；跨层协议仍为 1，配置 schema、用户入口与本地运行时选择不变。

当前不承诺启动画面仍保有已撤回方案的耗时，也不承诺任意真实项目的会话创建均为零延迟。
原本就需要的项目资源和扩展初始化仍由官方 SDK 处理；大历史、慢磁盘和用户扩展应继续根据
实际诊断分析。内置包增加安装体积；首次构建准备需要网络，缓存有效后可离线使用。
实际运行验证以 Windows x64 为准。`pix` 仅为参考，其源码误改已撤回。

本次以完整 SDK 就绪为前提的实测结果如下。

| 相同完整 SDK 的运行时评估，中位数 | Node 22.22.0 | Node 24.14.0 |
| --- | ---: | ---: |
| Bridge 握手 | 3251.89 ms | 2794.09 ms |
| 首次会话请求 | 55.59 ms | 47.47 ms |
| 后续会话请求 | 19.56 ms | 17.38 ms |

重新准备的正式内置资源在隔离空目录中，Bridge 握手中位数为 2549.58 ms，首次会话请求
48.53 ms，后续 15.68 ms。这些是空资源的进程基准，不是任意真实项目的点击响应保证。

原生验证使用相同的 SDK 资源及前端、独立应用标识的 Release 程序，通过 WebView2/CDP
等待启动遮罩退出，再直接测量原生命令的会话创建响应。两组均提前加载完整 SDK，每组三次。

| 原生中位数 | Node 22.22 对照 | 当前 Node 24.14 |
| --- | ---: | ---: |
| 窗口与工作台就绪 | 4302.20 ms | 3366.15 ms |
| 首次会话创建命令响应 | 2785.17 ms | 2728.14 ms |
| 后续会话创建命令响应 | 83.99 ms | 85.69 ms |

启动约改善 22%，首次与后续创建基本维持原有水平，没有把 SDK 导入成本加到首次操作。
原生首次会话的 `resource.reload` 约占 2.68 秒，是两组都存在的资源初始化成本，
不是已经移除的 SDK 补载。该部分尚不能宣称已经优化完成；后续应单独依据资源与扩展诊断优化，
不能通过跳过资源或扩展改变功能。原生对照首个样本出现 20.31 秒长尾，不以单次冷态比例宣传收益。

验证结果：`pnpm test` 共 755 项常规测试通过（8 项构建脚本、167 项 Bridge、
424 项 Renderer、156 项 Rust），一个依赖本地历史 fixture 的可选测试跳过，
一个性能基准默认忽略；`pnpm build` 通过，完整 SDK 就绪门禁测试和六次原生启动/会话检查通过。
各原始记录位于 `output/startup-ux-*.json`、`output/startup-ux-*.log`。

Bridge、Renderer 的 TypeScript 检查及 `cargo check --release` 通过。普通 `pnpm check`
在 debug 目录复制运行时资源时遭遇 `node.exe` 文件占用，因此没有将该次完整命令记为通过；
未为此关闭用户正在运行的程序。构建产生的跟踪内 TypeScript 增量文件已还原，不纳入变更。
